Workload & baseline

I begin with workload characterization and a stable baseline: throughput, latency, CPU utilization, core scaling, frequency behavior, memory bandwidth, and power.

Controlled experiment

I vary one meaningful dimension at a time, such as core count, NUMA placement, frequency, workload size, or precision, while keeping platform state and run conditions explicit.

Telemetry & hardware behavior

I correlate application behavior with EMON, PMU counters, IPC, TMA, cache, memory, frequency, uncore, I/O, and power signals to identify the limiting subsystem.

Root cause & optimization

I turn the measured bottleneck into a testable hypothesis, then evaluate system tuning, workload changes, graph optimization, operator pruning, feature fusion, or FP32/INT8 trade-offs.

Validation

I repeat the experiment, compare against the baseline, check regression behavior, and preserve telemetry and report artifacts so the result can withstand review.

Workload→Baseline→Controlled experiment→Telemetry / EMON→Root cause→Optimization→Validation

CPU scaling & bottleneck analysis

Does throughput keep pace with added CPU cores, or does it plateau?

Problem

Determine whether workload throughput scales with increasing CPU core count and identify where scaling efficiency begins to degrade.

Measurement

Throughput, CPU utilization, core count, CPU frequency, memory bandwidth, NUMA/SNC placement, and EMON/PMU counters.

Root cause

Correlated the throughput curve with CPU utilization and memory-system behavior to determine whether the workload was CPU-bound, memory-bound, or limited elsewhere.

Validation

Repeated the experiment across multiple core counts and confirmed the identified bottleneck moved consistently with the expected hardware signal.

Result — Scaling efficiency was not uniform across the core-count range; EMON telemetry showed the limiting subsystem shifting as core count increased.

Core vs. uncore frequency sensitivity

Does raising core frequency move the needle, or is the workload gated elsewhere?

Problem

Determine whether increasing core frequency produces a meaningful performance improvement, separate from uncore/memory sensitivity.

Measurement

Core frequency, uncore frequency, throughput, CPU utilization, memory bandwidth, and package power.

Root cause

Varied core frequency and uncore frequency independently to isolate which one the workload actually responded to.

Validation

Repeated the comparison across multiple uncore-frequency points to confirm the response tracked core frequency rather than another variable.

Result — Workload throughput tracked core-frequency changes more closely than uncore-frequency changes, identifying the available platform-tuning lever.

Compared scaling efficiency within a single NUMA/SNC domain against scaling that crossed domain boundaries.

Result — Scaling efficiency measurably changed when crossing domain boundaries, showing the workload is sensitive to platform topology, not just raw core count.

Redis / memtier characterization

What actually limits Redis/memtier throughput as resources increase?

Problem

Understand what limits Redis/memtier performance as CPU and memory resources increase, including the effect of hyper-threading.

Measurement

Throughput/IOPS, CPU utilization, core count, core and uncore frequency, memory bandwidth, package power, and HT on/off.

Root cause

Changed one variable at a time — cores, frequency, HT state — to determine whether the limit was CPU execution, memory bandwidth, or thread-level contention.

Validation

Repeated key comparisons, including HT on vs. HT off, to confirm the response was consistent with the suspected bottleneck.

Result — The dominant constraint varied with configuration; HT did not uniformly improve throughput, and the limiting resource shifted between CPU and memory bandwidth.
